Eliminate dual-implementation repos — deepen @chokro/db

Files involved

packages/db/src/index.ts apps/api/lib/database.ts apps/api/lib/repos/*.ts

Problem

Every repository method contains two complete implementations — one for Drizzle SQL, one for in-memory arrays — selected at runtime by databaseOrTestStore() which checks NODE_ENV === 'test'. This means:

  • Adding a new query filter requires editing both branches in the same function
  • The in-memory branch silently diverges from the SQL branch (different sort behaviour, missing constraints)
  • The memoryStore uses any[] — zero type safety for test data
  • @chokro/db exports raw Drizzle table symbols, forcing every repo to build raw queries

// listings.ts L26-37 — Every method has this dual-path structure

async create(values: CreateListingInput) {
  return databaseOrTestStore(
    async () => (await db.insert(listings).values(values).returning())[0],
    () => {
      const listing = { id: crypto.randomUUID(), ...values, created_at: new Date() };
      memoryStore.listings.push(listing);  // ← second implementation
      return listing;
    },
  );
}

Solution

Define a repository interface (TypeScript type) in @chokro/db, then provide two adapters: a DrizzleListingRepo and a MemoryListingRepo. Route handlers accept the repo through their module's interface — production wires the Drizzle adapter; tests wire the memory adapter. Delete databaseOrTestStore entirely.

Benefits — Locality & Leverage

Locality

A new query filter is one change in one adapter. The SQL and memory implementations are isolated — they can't silently diverge.

Leverage

The interface is the test surface. Tests swap the adapter at the seam — no NODE_ENV checks, no global mutable state, no any[].

Deepen route handlers — absorb shallow services into domain modules

Files involved

apps/api/lib/services/listingService.ts apps/api/lib/services/walletService.ts apps/api/app/api/listings/route.ts apps/api/app/api/auth/*/route.ts apps/api/lib/auth.ts

Problem

The current layer structure is Route → Service → Repo, but the services are pass-throughs that fail the deletion test. Meanwhile, the route handlers are doing the real work: Zod parsing, auth checks, business rules, and response formatting.

listingService — pass-through

// 4 of 5 methods are 1-line forwarding calls:
async getListingById(id: string) {
  return listingRepo.findById(id);
}
async getListingsByOwner(ownerId: string) {
  return listingRepo.findByOwnerId(ownerId);
}
async updateListingStatus(id: string, status) {
  return listingRepo.updateStatus(id, status);
}

Route handler — too fat

// auth/login/route.ts does ALL of this:
// 1. Zod parse body
// 2. Look up user by email (repo)
// 3. Compare password hash (bcrypt)
// 4. Sign JWT
// 5. Format response
// No authService exists!

Solution

Create domain modules (e.g., listingDomain, authDomain) that own validation, business rules, state transitions, and repo interaction. Route handlers become thin HTTP adapters: parse request → call domain module → format response. The shallow listingService and walletService get absorbed.

Benefits — Locality & Leverage

Locality

All listing business rules (transitions, ownership, validation) live in one file. Currently split between route handler, service, and repo.

Leverage

Domain modules are testable without HTTP. Auth logic (hash, JWT, token validation) becomes reusable across REST routes, admin, and future websocket handlers.

Seal the mobile network seam — encapsulate auth tokens

Files involved

apps/mobile/src/services/api.ts apps/mobile/src/context/AuthContext.tsx apps/mobile/src/hooks/*.ts

Problem

The network module (services/api.ts) forces every caller to manually pass { token }. Every hook must: (1) import useAuth, (2) destructure token, (3) pass it to apiRequest. This is a leaky seam — auth knowledge bleeds into every data-fetching module.

// useFeed.ts — this pattern repeats in ALL 5 hooks

export function useFeed(category, condition) {
  const { token } = useAuth();           // ← every hook does this
  return useInfiniteQuery({
    queryFn: async ({ pageParam }) => {
      return apiRequest('/api/feed?...', { token });  // ← and this
    },
    enabled: !!token,                     // ← and this
  });
}

Solution

Make apiRequest a deep module that internally resolves the auth token (e.g., by reading from storage or accepting a token-provider function at initialization). Hooks drop the useAuth import, the token destructuring, and the enabled: !!token guard. If auth changes (token refresh, new header format), the fix is one file — not five hooks.

Benefits — Locality & Leverage

Locality

Auth token threading changes once in the network module, not across 5+ hooks and every future hook.

Leverage

Adding token refresh, retry-on-401, or switching to cookie-based auth becomes a single-module change. Hooks get simpler interfaces.

Consolidate category/unit domain logic into @chokro/shared

Files involved

packages/shared/src/dto/listings.ts apps/mobile/src/types.ts apps/api/app/admin/lib/formatters.ts apps/api/app/admin/drop-zones/categories.ts

Problem

The rule "APPLIANCES and E_WASTE use piece; everything else uses kg" is a core domain invariant that's implemented three times in three different places:

1. packages/shared/src/dto/listings.ts:L12-20 — Zod .superRefine()

2. apps/mobile/src/types.ts:L25-32 — unitForCategory() function

3. apps/api/app/admin/lib/formatters.ts:L5-14 — another unitForCategory()

Adding a new category (e.g., TEXTILES) requires touching all three files. Locality is zero.

Solution

Move unitForCategory(), formatLabel(), and the category→unit mapping into @chokro/shared as a single category domain module. All three consumers import from one place.

Benefits — Locality & Leverage

Locality

Adding a new category is one change in @chokro/shared. The Zod validation, mobile UI, and admin formatters all derive from the same source.

Leverage

3 consumers today, N consumers tomorrow. The category module becomes the canonical source of truth for the rate card, listing creation, and admin management.

Speculative

Delete dead re-export files in mobile

Files involved

apps/mobile/src/api.ts apps/mobile/src/storage.ts

Problem

Two files exist at the root src/ level that simply re-export from src/services/: 

// src/api.ts — entire contents
export * from './services/api';

// src/storage.ts — entire contents
export * from './services/storage';

Deletion test: deleting these files would not scatter complexity — it would simply require callers to import from the canonical services/ path. Zero depth, zero leverage.

Solution

Delete both files. Update any imports that reference @/api or @/storage to use @/services/api and @/services/storage directly. This is a 5-minute cleanup.

Why speculative?

Low impact — this is cosmetic cleanup. Modules with zero depth are harmless when they're small. Pursue only if you're already touching these files.

🎯 Top Recommendation

Start with Candidate #1: Eliminate dual-implementation repos

This is the highest-leverage, highest-locality fix in the codebase. Every feature you build touches the repository layer. Every time you add a query filter, you write it twice. Every test runs against an any[] memory store that silently diverges from your actual SQL.

Candidate #2 (deepening route handlers) follows naturally — once repos have clean interfaces, services can be absorbed into domain modules that own the full vertical: validation → business rules → persistence.

Sequence

#1 → #2 → #3. Each candidate unlocks the next.

Risk

#1 and #2 touch ~20 files. Plan for a focused sprint, not a drive-by fix.

Quick win

#4 (consolidate category logic) can be done in parallel — small, safe, high locality payoff.
