🔌 2. Candidate 1: Eliminate Dual-Implementation Repos

Why having if (NODE_ENV === 'test') inside database queries is dangerous, and how the Repository Adapter fixes it.

🚗 The Electric Car Analogy

Imagine building an electric car. But whenever you press the accelerator pedal, the car checks: "Are we in a video game simulation, or driving on a real highway?" If simulation, it spins fake plastic wheels. If highway, it spins real rubber tires.

Why is this bad? Your real engine code is cluttered with video-game simulation code! If you change one, you might accidentally break the other.
The Solution (The Universal Plug / Adapter): Build one standard wheel socket (Interface). In production, plug in Real Tires. In tests, plug in Simulation Rollers. The car engine never contains an if (isTest) statement!

❌ BEFORE: Tangled Dual Branching
export async function createListing(data) {
// BAD: Every function checks NODE_ENV!
if (process.env.NODE_ENV === 'test') {
memoryStore.listings.push(data); // Fake test store
return data;
}

// Real Postgres Drizzle query
const res = await db.insert(listings).values(data);
return res;
}

⚠️ Problems: Production code is polluted with test arrays. Hard to maintain, no type safety for test mocks, impossible to test edge cases cleanly.

✅ AFTER: Clean Repository Adapter
// 1. The Interface (The Universal Contract)
interface ListingRepository {
create(data: NewListing): Promise<Listing>;
}

// 2. Real SQL Adapter (Used in Production)
class DrizzleListingAdapter implements ListingRepository { ... }

// 3. Fast Memory Adapter (Used in Tests)
class MemoryListingAdapter implements ListingRepository { ... }

✨ Benefits: Zero if (isTest) checks. Production code stays 100% pure SQL. Tests run instantly in memory without a live database server.

👨‍🍳 3. Candidate 2: Domain Layer vs Fat Route Handlers

Why the Waiter shouldn't cook, and why the Chef should own all the business rules.

🍽️ The Waiter vs Chef Problem

In our old code, the Route Handler (the Waiter) was doing everything:
1. Checking if the user's password matched bcrypt hashes.
2. Verifying if the recycled weight was greater than zero.
3. Calculating eco-points based on rate cards.
4. Writing the JSON response.

Meanwhile, the Service layer was an empty shell that did nothing!
The Fix: Put all business rules (called Invariants) inside Domain Modules (authDomain, listingDomain, walletDomain). The Route Handler only handles HTTP inputs and outputs.

❌ BEFORE: Overburdened Waiter (Route)
// /api/listings/route.ts
export async function POST(req) {
// Waiter parsing raw JSON manually
const body = await req.json();
if (body.weight <= 0) return Response.json({error: 'Invalid weight'});
if (!VALID_CATEGORIES.includes(body.category)) ...
const points = body.weight * 30; // Inline math!
const token = signJWT({ userId: body.userId });
return Response.json({ success: true, points });
}
✅ AFTER: Clean Separation of Concerns
// 1. The Waiter (Route Handler): Pure HTTP Adapter
export async function POST(req) {
const data = await parseBody(req, CreateListingSchema);
const result = await listingDomain.createListing(data);
return Response.json(result);
}

// 2. The Master Chef (Domain Module): Owns all rules
class ListingDomain {
async createListing(data) {
this.assertUserNotSuspended(data.userId);
this.validateDropZone(data.dropZoneToken);
return this.repo.create(data);
}
}

📖 5. The Beginner's Jargon Buster

Demystifying software engineering terms used in these proposals.

Invariant
"The House Rules"
A rule that must never be broken in the system. (e.g. "A wallet balance cannot be negative", "You cannot drop off waste at a deactivated bin").
Repository Pattern
"The Warehouse Manager"
A software layer that acts as a collection of items in memory. The rest of the app asks the repository for data without knowing if it's stored in Postgres, MySQL, or a temporary array.
Decoupling
"Lego Bricks vs Superglue"
Designing code so that changing one part (like switching database engines or changing the UI) does not break unrelated parts of the app.
Drizzle ORM
"The TypeScript-to-SQL Translator"
A modern tool that lets us write TypeScript code that safely generates fast SQL queries for our PostgreSQL database.

🚀 6. The Action Plan: What We Will Implement

Our step-by-step roadmap to implement the remaining backend improvements.

Phase 1: Deepen Database Layer (Candidate #1)
Step 1 — Foundation
  • Create clean TypeScript repository interfaces in packages/db (ListingRepository, WalletRepository, UserRepository).
  • Implement DrizzleListingAdapter for production SQL.
  • Implement MemoryListingAdapter for fast automated tests.
  • Remove databaseOrTestStore() and all NODE_ENV === 'test' branching from repos.
Phase 2: Deepen API Domain Modules (Candidate #2)
Step 2 — Business Logic
  • Create domain modules (authDomain, listingDomain, walletDomain) that own validations, state transitions, and rate card calculations.
  • Refactor Next.js API route handlers to become lightweight HTTP adapters.
  • Add comprehensive unit tests for all domain rules.
