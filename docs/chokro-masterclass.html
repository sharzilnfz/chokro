Part 0

🧠 The Big Picture

Imagine a market with three counters. At the front, buyers and sellers hand things over and ask questions — that's the mobile app. Behind it, an office checks every request, decides yes/no, and writes receipts — that's the API server. And in the back room, one trusted ledger book records everything that is true — that's the database. The front desk is the only thing you ever see, but every "yes" comes from the office, and the office only trusts the ledger.

Chokro is exactly that. A phone app (Expo / React Native) asks a server (Next.js, which also serves the admin website) to do things, and the server reads and writes a single PostgreSQL database through Drizzle ORM. Nothing on the phone talks to the database directly — every data change travels through an HTTP call to the server.

client apps (phone + admin web) API server (rules & gates) database (source of truth) tokens & signatures

🔑 One Request, End-to-End

Every door in Part 1 works the same way. If you understand one route you understand all 22. Let's live inside POST /api/listings — the request the phone fires when Sadia creates a listing.

The request as the server sees itwhat leaves the phone
Walk the route — press each stageeach stage is one ingredient of the skeleton below

Every route shares this skeleton

export const POST = safeRoute(async (req: Request) => { // ① safeRoute: try/catch → routeError, + stamps CORS headers on every response
  const auth = requireAuth(req);                    // ② gate: Bearer JWT → {userId, email, role} or 401
  if (auth.response) return auth.response;          // ③ early return if the gate failed

  const parsed = Schema.safeParse(await req.json()); // ④ validate body with a zod schema
  if (!parsed.success)                              // ⑤ bad data → canonical apiError response
    return apiError('Invalid input', 400, parsed.error.format());

  const listing = await listingRepo.create({ ... }); // ⑥ domain repository encapsulates DB vs test store
  return apiSuccess('Listing created', { listing }, 201); // ⑦ JSON out, CORS-stamped — apiSuccess/apiData/apiError keep the shape uniform
});                                                 // safeRoute catches unhandled errors → routeError (500/503)

The real file is a few more lines (the zod schema for listings also enforces the kg-vs-piece rule — that's a whole story, see Part 4). But the shape is identical across all 22 endpoints: a thin route wrapper, an auth gate, a zod parse, a repository call that hides the Postgres-vs-`memoryStore` twin, and one of the three response helpers (apiSuccess/apiData/apiError). Cross-cutting note: because the mobile app can now run in a browser, safeRoute also stamps Access-Control-Allow-* headers on every success and error, and each route exports an OPTIONS handler for the browser's CORS preflight (see Part 4.5).

Production database vs. test twinthe one weird thing in every route

Every route can run one of two code paths. Click to see which.

⚡ TRAP 2.1Every route has two parallel back-ends. In dev it writes to real Postgres; when tests set NODE_ENV=test, the @chokro/db package hands you an in-memory array (the memoryStore) and db is literally null. The in-memory tier mirrors all six tables so Jest tests run with no database installed. New data shapes must be added to both the real insert and its memoryStore twin.
⚡ TRAP 2.2Postgres returns decimals as strings. The schema stores money and weight as decimal; Drizzle hands those back as text like "45.00". That's why the code does priceBdt.toString() when writing and Number(txn.amount) when reading. Never add "string money" without a Number() first.
Self-test: a test signs up a user, but the test crashes with "Database unavailable". What happened, and what's the fix?
Reveal

The test probably ran with NODE_ENV set to something other than test, so databaseOrTestStore tried the real database. Run Jest with NODE_ENV=test — then every route takes its in-memory path instead.

Part 2.5

🌐 Networks — how the app on the web talks to the API

Sprint 2 changed one thing that ripples through the whole server: the phone app now runs in a browser. When a phone (React Native) talks to the API it's just an HTTP call. But when the same app is served as a web page and fetches http://localhost:3000/api/* from a different origin, the browser steps in with CORS (Cross-Origin Resource Sharing) and silently blocks every response unless the server explicitly says it's allowed.

// apps/api/lib/http.ts — one constant, stamped on every response via safeRoute
const CORS_HEADERS = {
  'Access-Control-Allow-Origin': '*',                                   // any origin may read
  'Access-Control-Allow-Methods': 'GET, POST, PUT, PATCH, DELETE, OPTIONS',
  'Access-Control-Allow-Headers': 'Content-Type, Authorization, X-Requested-With',
};
export function OPTIONS() { return new NextResponse(null, { status: 204, headers: CORS_HEADERS }); }  // preflight
How CORS actually flowspick a scenario to see what the browser does
① Safe read (GET)
Browser sends GET /api/feed with an Origin: header. The route runs, safeRoute stamps Access-Control-Allow-Origin: * on the response. Browser sees the match → hands the JSON to the web app.
② Non-simple request (POST + JSON)
POST with Content-Type: application/json triggers a preflight: the browser first fires OPTIONS /api/listings. Our OPTIONS() handler answers 204 with the CORS headers → browser then sends the real POST.
③ Without CORS headers
The fetch actually reaches the server and the DB runs — but the browser withholds the response from JavaScript. The request "fails" from the app's view even though the server replied 200. This is why CORS feels like the server is "broken" when it isn't.
⚡ TRAP 2.5.1Errors were invisible on web before this. Before CORS headers were added to routeError and every helper, a 400/500 from the API showed up in the web app only as a generic "Failed to fetch" — the browser hid the real body. Now safeRoute stamps the headers on the error path too, so a validation 400 is readable as JSON on web.
Self-test: why does GET /api/health (no body, no custom headers) not trigger a preflight, but logging in does?
Reveal

A plain GET with no custom headers is a "simple request" — the browser sends it directly. The login POST uses Content-Type: application/json, which is not a "simple" content type, so the browser fires the OPTIONS preflight first. That's why routes export an OPTIONS handler even though there's no POST body to speak of on the preflight itself.

Part 3

🔐 Identity & Trust

Two files do all the security: apps/api/lib/auth.ts (passwords + tokens + role gates) and apps/api/app/api/partners/apply/route.ts (partner trust). This part answers the two front-door questions: "Who are you?" → requireAuth — and "Can you do that?" → requireAdmin.

1 · Passwords are never stored

// bcryptjs — one-way, salted, deliberately slow
hashPassword(pw)         // "letitgo" → "$2b$10$WLnQ…" (never reversible)
comparePassword(pw, hash)  // only answers "yes" / "no" — signup & login use it

Signup runs the raw password through hashPassword (bcrypt.hashSync(pw, 10)), stores only the hash, and always saves role: 'INDIVIDUAL'. Login re-hashes your attempt and compares — the plain-text password never reaches the database.

2 · The token (a badge you carry)

On successful login the server mints a JWT with jsonwebtoken: the payload holds { userId, email, role }, the server signs it with the JWT_SECRET (HMAC-SHA256), and it expires in 7 days. From then on the phone sends it on every request as Authorization: Bearer <token>. Hover each segment below.

JWT anatomy — hover a segmentdemo for user@chokro.org
// lib/auth.ts — the two gatekeepers
export function requireAuth(req) {
  const user = verifyAuthHeader(req);        // read Bearer → verifyToken → parse role
  if (!user) return { response: NextResponse.json({error:'Unauthorized'}, {status:401}) };
  return { user };
}
export function requireAdmin(req) {
  const auth = requireAuth(req);            // 1. must be logged in
  if (auth.response) return auth;
  if (auth.user.role !== 'ADMIN')           // 2. must be an admin
    return { response: NextResponse.json({error:'Forbidden'}, {status:403}) };
  return auth;
}
⚡ TRAP 3.1The token is signed, not encrypted. The middle segment is just base64 of the JSON payload — readable by anyone. Its safety comes from the signature: only someone holding JWT_SECRET can create one, so a tampered payload fails verification. Never put secrets in it.
⚡ TRAP 3.2The role is trusted from the token. requireAdmin does not re-query the database. If a user is promoted to ADMIN in the DB, their existing 7-day tokens still carry the old role until they log in again. Fine for a demo, unacceptable in production.

3 · The partner DoE gate — a trust rule worth memorizing

This is the best example of a business invariant in the whole repo. The PRD says e-waste routes may only go to DoE-licensed partners, and nobody gets that by declaring it themselves.

Press each scenariothe same flow, three different legal outcomes
Why this matters: even when the request claims eWasteLicensed: true with a doc attached, the route hard-sets e_waste_licensed: false in the database. That flag is only flicked to true later by POST /api/admin/partners when an admin approves a partner who has a DoE license doc on file. The applicant offers a fact; an admin confirms it. The code never lets users self-certify.
Self-test: someone signs up and self-registers as PARTNER. Two days later their application shows "VERIFIED". What chain made that possible?
Reveal

Signup always writes role INDIVIDUAL — a user can never be born an admin. Being a partner is two steps: POST /api/partners/apply (any logged-in user) creates an APPLIED row; only POST /api/admin/partners by a real admin flips it to VERIFIED. That's the whole "privilege escalation" story the code lets you see.

Part 4

🔄 The Marketplace (Listings & Feed)

Three ideas make up this area: the unit rule that turns categories into physical quantities, the status machine listings move through, and the cursor pagination that pages the browse feed without page numbers.

1 · Dual-unit validation

Recycling pricing in Bangladesh is dual-unit: scrap materials and clothes are priced per kg, appliances and e-waste are priced per piece (BanglaBin-style rate cards, per the PRD). The create-listing schema enforces it with a superRefine:

const isPieceCategory = category === 'APPLIANCES' || category === 'E_WASTE';
if (isPieceCategory  && (unit !== 'piece' || pieceCount === undefined || weight given)) ⇒ reject
if (!isPieceCategory && (unit !== 'kg'     || declaredWeight === undefined))            ⇒ reject

3 · Cursor pagination ("the page that never skips")

The feed route takes limit (up to 50) and an opaque cursor. The cursor is just where we left off — the createdAt + id of the last item you saw, base64-encoded:

// feed/route.ts
encode:  Buffer.from(JSON.stringify({ createdAt, id })).toString('base64url');
decode:  JSON.parse(Buffer.from(value, 'base64url').toString());
filters.push( or( lt(created_at, cursor.createdAt),          // strictly older…
                  and(eq(created_at, cursor.createdAt), lt(id, cursor.id)) ) );  // …or same-tick, smaller id
Watch the cursor do its jobpress "Load more" — no page numbers anywhere
⚡ TRAP 4.1Cursor = sort-position of the last seen row. That's why created_at alone isn't enough — two items in the same millisecond share a timestamp, so the id is the tiebreaker. And the route fetches limit + 1 rows on purpose: the extra one proves hasMore (there is a next page) and is then dropped.
Self-test: the client asks for 20 items, the database has 41 ACTIVE. What does the server return, and what happens on the second request?
Reveal

First call returns 20 items + a cursor (the 21st row is fetched only to prove more exist). The second call carries that cursor and returns rows 21–40 + a new cursor; the third returns the last row with nextCursor: null. On the phone, "Load more" simply stops rendering.

Part 5

💰 The Ledger (Rate Card + Wallet)

Two systems, one philosophy: don't store a derived value — store events and derive on reading. The rate card stores every published version and the app shows the current one; the wallet stores every credit transaction and the balance is a sum, never a stored number.

1 · Rate card with versioning

Admins publish rates by inserting a new row. The public route (GET /api/rate-card/published) filters out future effective_from dates, then keeps the newest row per category|condition|unit — the "current price" is derived, not stored:

Who wins? — click "add" to publish a newer pricegreen = the version the app actually serves
// rate-card/published route — the whole algorithm
.filter(e => new Date(e.effective_from) <= now)            // not alive yet? ignore
.reduce((acc, entry) => {
   key = `${entry.category}|${entry.condition_band}|${entry.unit}`;
   acc[key] = !acc[key] || new Date(entry.effective_from) > new Date(acc[key].effective_from)
                ? entry : acc[key];                         // newest row wins the key
})
⚡ TRAP 5.1The admin web page offers a condition called SCRAP (CONDITION_BANDS in admin/rate-card/page.tsx), but the shared Condition enum knows only EXCELLENT · GOOD · FAIR · POOR — pick SCRAP in the console and the API answers 400, because the zod schema validates against the shared enum. The condition list is duplicated in two files, and they've already drifted.

2 · The wallet: an append-only ledger

Every credit movement is one row in credit_txns (kind EARN / REDEEM / ADJUST, status PENDING / VERIFIED / REJECTED). The database literally refuses to ever change or delete a row — a trigger reject_credit_txn_mutation raises 'credit_txns is append-only' on UPDATE/DELETE (see packages/db/src/migrate.ts).

The balance route (GET /api/wallet/balance) reads all the user's rows and sums: verified positives → verified balance, pending rows → pending. Nothing is stored; it's always recomputed. Click any row below.

Click any row — watch the balance derivefrom the ledger, never stored
⚡ TRAP 5.2Because rows can't be edited, "fixing" a wallet means appending a new ADJUST row — POST /api/admin/wallet/adjust does exactly that. Negative amounts claw credits back, and the reason (at least 5 characters) is mandatory so every adjustment stays auditable.
Self-test: an admin "adds 100 credits" but the user's balance still shows 0. Where should you look first?
Reveal

Check the transaction's status. If it's PENDING or REJECTED it isn't part of verifiedSum, so it never reaches the spendable balance. The wallet only counts VERIFIED rows.

Part 6

📟 Signed QR Drop Zones

Drop zones are physical boxes on campus. They print a poster; the poster has a QR code; the phone scans it and asks the server "which zone is this?" — but only if the QR proves it was created by Chokro.

// lib/qr.ts — the anti-tamper layer
function signature(payload) { return createHmac('sha256', QR_SECRET).update(payload).digest('base64url'); }
createQrToken() => payload = 32 random bytes (base64url)
                   token = payload + '.' + signature(payload)
isValidQrToken(token) => recompute signature and timingSafeEqual  // constant-time compare
Zone lifecycle — press each stageadmin prints → user scans → server resolves
⚡ TRAP 6.1Signing ≠ secrecy. The random 32-byte payload tells you nothing; the signature is what proves the token wasn't made up. Anyone can read a token — only the server holding QR_SECRET can forge one. And timingSafeEqual makes the check resistant to timing attacks.
Why so heavy? A QR code on a wall is public. If scanning a zone were just "upload this ID", a scammer would print one for a fake campus. The signature means a printed token can't be forged; the resolve route then returns the zone's name, status, and accepted categories — recognized, not deposited. (Deposits & credits are a later sprint.)

Sprint-2 round-up: web, NativeWind, and platform-safe storage

🎨 NativeWind (Tailwind for RN)
Styles used to be hand-written StyleSheet.create({...}) objects in every screen. The whole app was migrated to NativeWind v4 (nativewind@4.2 + react-native-css-interop + tailwindcss@3.4): screens now use utility classNames (className="bg-surface p-4 rounded-xl") and shared tokens come from tailwind.config.js / global.css. One design language, and it compiles to real RN styles — plus it's the reason the app can now target web.
💾 storage.ts — one token store, three platforms
expo-secure-store doesn't exist on web. src/storage.ts wraps it: on iOS/Android it uses the secure keychain/keystore; on web it falls back to localStorage; everywhere it swallows failures gracefully (returns null instead of throwing). Same API everywhere — storage.getItem('jwt') works on all three.
🔀 API URL resolution got smart
On a physical phone, localhost means the phone itself, so dev uses a LAN IP. But that same LAN-IP config breaks web served on the laptop. src/api.ts now detects Platform.OS === 'web' && hostname === 'localhost' and rewrites a LAN-IP base to http://localhost:3000 automatically — one config value works for both phone and web.
// src/api.ts — the tiny HTTP client every screen uses
const configuredUrl = EXPO_PUBLIC_API_URL || expoConfig.extra?.apiUrl;   // may be a LAN IP for phones
const API_URL = String(configuredUrl || "http://localhost:3000").replace(/\/$/, '');
//   └─ on web + localhost: a 192.168.x / 10.x base is rewritten to localhost:3000
apiRequest(path, { token, ... }) => fetch(`${API_URL}${path}`, { headers: {
  Accept, 'Content-Type' (only when there's a body), Authorization: `Bearer ${token}` }});
// any non-2xx → throw ApiError(message, status); each screen turns it into a friendly line
Mode switch: apps/mobile/.env.local currently points EXPO_PUBLIC_API_URL at a LAN IP (e.g. http://192.168.1.200:3000). On a physical phone that must be your dev machine's LAN address on the same Wi-Fi; on emulators and (now) web you can use http://localhost:3000 — and the web case is automatic thanks to the resolver above. The web pages hitting that URL need the CORS headers from Part 2.5.

2 · The admin console (web)

Three tools: the partner verification queue (fetchPartners / handleVerify → POST /api/admin/partners), the rate-card editor (POST /api/admin/rate-card), and the drop-zone registry — in apps/api/app/admin/*/page.tsx. Part 8

🐳 Deploying — Docker & Compose

Sprint 2 also taught the app to leave the laptop. Two files do it: a repo-root multi-stage Dockerfile that turns apps/api into a tiny self-contained image, and compose.yaml that wires the API to Postgres.

1 · The Dockerfile (4 stages)

base
node:22-alpine + corepack → pnpm. The common ancestor for every stage, so the lockfile + Node version are identical everywhere.
deps
Copies only package.json / pnpm-lock.yaml / pnpm-workspace.yaml and every workspace's package.json, then pnpm install --frozen-lockfile into a cached mount. Changing source code does not bust this layer's cache.
builder
Copies node_modules + source, runs pnpm turbo run build --filter=@chokro/api. Produces apps/api/.next/standalone — Next.js' self-contained server bundle (no separate node_modules needed).
runner
Fresh image, NODE_ENV=production, non-root nextjs user, copies only the standalone output + static assets, then CMD ["node", "apps/api/server.js"] on port 3000. Security + tiny footprint.

2 · docker compose — three services

# compose.yaml
postgres   postgres:17-alpine · healthcheck pg_isready · persisted volume chokro-postgres
              └─ capped at 384M RAM / 1.0 CPU (low-memory tuning)
api        builds the Dockerfile · waits on postgres being healthy (not just up)
              └─ env: DATABASE_URL → postgres:5432/chokro, JWT_SECRET, QR_SECRET
db-setup   one-shot, on the setup profile: db:push && db:migrate && db:seed
              └─ opt-in — only runs with docker compose --profile setup up
Two things worth stealing from this file: (1) depends_on: condition: service_healthy means the API never races a half-booted Postgres. (2) The setup profile keeps the seeding service out of normal up — you bring it up once to hydrate the DB, then forget it.
⚡ TRAP 8.1CORS is what makes a containerized web app work. When the Expo app is served from one host/port and the API runs in Docker on :3000, they are different origins — without the Part 2.5 headers the web app sees nothing. The Dockerfile and the CORS layer were added together for exactly this reason.
Self-test: you run plain docker compose up -d and the API is up, but login fails with "no rows". What's missing?
Reveal

Database seeding is behind the setup profile, which normal up doesn't run. Run docker compose --profile setup up db-setup once (or pnpm db:setup against the exposed :5432) to create the schema and the demo accounts.
